# IT特化 求人マッチングサービス 要件定義書

## 1. プロジェクト概要

- **サービス名**: Tech Match(前作から引き継ぐ)
- **種別**: 求人マッチングサイト(Wantedlyをモデルに機能を絞り、マッチングアプリの手法を取り入れる)
- **対象職種**: IT・エンジニア職に限定
- **目的**: 就職活動用ポートフォリオ
- **プラットフォーム**: Webアプリ
- **前作との違い**: 前作(`~/Desktop/Match-Portfolio`)は完成度が低かったため作り直す。機能数は増やさず、**企業ページと求人票の質**を重点的に高める。Stripe課金とメッセージ機能は削除する

### 1.1 解決する課題

- お互い入社する確率が低い時は面接時間の無駄になりやすい
- 応募のたびに履歴書・職務経歴書を用意する手間がある
- 書類選考の結果を長期間(あるいは無期限に)待たされる、いわゆる「サイレントお祈り」が起きる
- スカウト型サービスは応募者側の意志が弱く、的外れなアプローチが多い
- 求職者が「いいね」を乱発すると、企業が受け取る応募の質が下がる
- 求人票が自由記述だけだと、企業の雰囲気や開発環境が伝わらず、条件面でしか比較できない

### 1.2 コンセプト

- プロフィールを一度作れば、それが履歴書・職務経歴書代わりになり、求人ごとに書類を用意する手間をなくす(ただし志望動機のみは、企業への熱意を伝えるため応募ごとに個別入力する)
- 企業は「いいね」に対して7日以内に反応する必要があり、応募者を無期限に待たせない
- 「いいね」に月間上限を設けることで、応募を厳選させ、企業が受け取る応募の質を担保する
- 企業ページ・求人票を項目ごとに構造化し、カルチャー・技術スタック・働き方まで比較できるようにする

## 2. ユーザーロール

- **求職者(Job Seeker)**: 求人を検索し、応募する側
- **企業(Company)**: 企業ページ・求人を掲載し、応募者を選考する側

## 3. マッチングフロー

検索・応募型。「いいね」は求職者側からのみ行え、それ自体が応募の意思表示となる(企業からのスカウトはなし)。

1. 求職者が求人を検索・閲覧
2. 気になる求人に「いいね」(=応募)
3. 企業が7日以内に「気になる」か「見送り」を返す
   - 「気になる」: マッチ成立し、企業側に求職者のメールアドレス(ログイン用)が開示される
   - 「見送り」: 不成立。求職者は7日を待たずに結果が分かる。同じ求人には再度いいねできない
   - 7日以内に返さなかった場合: 自動的に不成立。同じ求人に再度いいねできる
4. マッチ成立後の連絡(面接日程調整・選考結果連絡)は、企業から求職者へメールで行う。アプリ内メッセージ機能・選考ステータス管理機能は設けない

**このサービスの役割はマッチ(応募の流入)まで**とする。実際の採用では、企業は複数の求人サイト・エージェント等からの応募をATS(採用管理システム。HRMOS採用・HERP Hire等)でまとめて管理しているため、選考管理は企業側の仕組みに任せる。ATSとのシステム連携(API連携)は行わない。マッチ前は求職者・企業どちらの連絡先も相手に公開されない

## 4. 機能要件

### 4.1 共通

- 会員登録・ログイン・ログアウト(Laravel Sanctum, SPA認証)
- パスワードリセット
- プロフィール編集

### 4.2 求職者向け機能

- プロフィール作成・編集(氏名・生年月日[18歳以上60歳以下]・自己紹介コメント[200文字程度]・ポートフォリオURL[GitHub・個人サイト等]・アイコン画像)
- 職歴の登録・編集・削除(複数件、0件可)
  - 項目: 会社名、在籍期間(開始年月〜終了年月。終了年月が未入力なら「在籍中」)、雇用形態
- 学歴の登録・編集・削除(複数件、0件可)
  - 項目: 学校名のみ
- 資格の登録・編集・削除(複数件、0件可)
  - 項目: 資格名のみ
- 求人検索・絞り込み
  - 条件: 技術スタック(タグ、複数選択可) + 職種 + 勤務地 + 雇用形態 + キーワード
  - 異なる条件同士はAND(例: 東京 + PHP → 勤務地が東京 かつ PHPを使う求人)
  - 技術スタックを複数選択した場合もAND(例: PHP + React → 両方を使う求人のみ)。使うフレームワークまで含めて希望に合う求人を絞り込めるようにするため
  - 職種を複数選択した場合も、技術スタックと揃えてAND(例: バックエンド + SRE → 両方の職種が設定された求人のみ)
  - 給与(月給)は表示するが、絞り込み条件にはしない
  - 勤務地には都道府県に加え「リモート」を選択肢として含める
  - レイアウト: PCでは求人一覧の横に検索サイドバーを常時表示する。スマホでは検索条件を一覧上部のドロップダウン(折りたたみ)にまとめ、タップで開閉する(Wantedlyのスマホ版と同様)
  - 求人一覧の各求人にはいいね数(=応募数)を表示する
  - 初回公開から30日以内の求人には「NEW」ラベルを表示する(募集再開ではリセットしない)
  - 並び替え: 「新着順」(デフォルト)と「人気順」を切り替えられる
    - 新着順: 初回公開日時の新しい順。新しい求人が埋もれないよう、こちらをデフォルトにする
    - 人気順: 直近30日のいいね数が多い順(同数なら新着順)。累計いいね数だと公開期間の長い求人が上に居座るため、「今注目されている求人」を出す。30日はNEWラベルの期間と揃えている
    - カードに表示するいいね数は累計のまま(並び替えの基準とは別)
  - 表示件数: 1ページ24件のページネーション(24件は1〜4列のどれでも割り切れるため)。当初の「もっと見る」ボタンから、ページごとにURLが決まり、戻ったときに同じページに戻れるページネーションに変更
  - いいね数・人気順は最大5分遅れて反映される(キャッシュのため。詳細は`FRONTEND_STRUCTURE.md`)
- 求人詳細閲覧(4.3の求人票構成で表示)
- 企業ページ閲覧(4.3の企業ページ構成で表示)
- 求人への「いいね」(=応募)
  - 志望動機(自由記述、必須)を応募ごとに入力する
  - 通常の「いいね」は**月5件まで**(月初にリセット)。当初は10件だったが、応募をより厳選してもらうため5件に変更
  - 「スーパーいいね」は通常の上限とは別枠で**月1件まで**(月初にリセット)。企業側の応募者一覧で視覚的に区別して表示する。反応期限(7日)は通常の「いいね」と同じ
  - 同一求人への重複応募は不可。ただし期限切れで不成立となった求人には再度いいねできる(見送られた求人は不可)
- 応募状況の確認
  - 1ページ内で「いいね済(反応待ち)」「マッチ」「不成立」の3タブで切り替える(マッチ専用ページは設けない)
  - ヘッダーには❤️アイコンのみを置き、このページへリンクする
  - マッチ成立した応募には「企業から登録メールアドレス宛に連絡が届きます」と表示する
  - マッチ成立後に企業から連絡が来ない場合は、本サービスの責任範囲外とする(アプリ内で連絡を完結させても防げない問題のため)
- 求人のブックマーク
  - 気になる求人を保存しておける(いいね=応募とは別。月間上限の対象外)
  - 対象は求人のみ(企業ページはブックマークできない)。件数上限なし
  - 企業側にはブックマークされたことは見えない
  - 応募状況とは別に、ブックマーク一覧ページを設ける。ヘッダーには🔖アイコンのみを❤️の横に置く
  - いいねした後もブックマークは残し、一覧に応募状況のバッジ(いいね済 / マッチ / 不成立)を表示する。不成立後に再度いいねした場合は、最新の応募の状況を表示する
- 通知(マッチ成立・不成立[見送り・期限切れ]。アプリ内通知のみ)

### 4.3 企業向け機能

- **企業ページ**の作成・編集。以下の順で表示する
  1. 簡単な自己紹介(会社名・アイコン/ロゴ・短い紹介文)
  2. 事業内容
  3. カルチャー(チーム構成・開発の進め方・レビュー文化など)
  4. 技術スタック(タグ)
  5. 働き方(リモート可否・フレックス等。マスタから選択するタグ形式。自由記述欄は持たない)
  6. 写真ギャラリー(最大5枚。登録順で表示)
  7. 基本情報(設立年・メンバー数[人数を数値で入力]・所在地[都道府県+市区町村以下]・WebサイトURL)。連絡は企業から求職者へ行うため、企業の電話番号・連絡用メールアドレスは持たない
  8. 募集中の求人一覧(公開中の求人を自動表示)
- 技術スタックは、運営側があらかじめ登録したマスタから選択する(自由入力は不可)。企業ページ・求人票・求人検索で同じタグを共通利用する
- 職種もマスタから選択する。後から職種を追加する際にコード修正が不要になるよう、enumではなくマスタテーブルで管理する。初期データ:
  - 開発: バックエンド / フロントエンド / フルスタック / iOS / Android / 組み込み・IoT / ゲーム
  - インフラ: インフラ / SRE / クラウド / ネットワーク / セキュリティ
  - データ・AI: データエンジニア / データサイエンティスト / 機械学習エンジニア
  - 品質・運用: QA・テスト / 社内SE・情報システム
  - マネジメント: テックリード / エンジニアリングマネージャー / プロジェクトマネージャー / プロダクトマネージャー
  - その他: UI/UXデザイナー / Webディレクター / セールスエンジニア / ITコンサルタント
- **求人票**の投稿・編集・削除・公開/非公開切り替え。以下の項目で構成する
  1. 画像ギャラリー(最大5枚)
  2. 仕事内容
  3. 求める人材
  4. 技術スタック(タグ。ポジションごとに設定)。1求人につき5つまで(職種と同じく、検索に多く出るための付けすぎを防ぐため)
  5. 条件(職種・雇用形態・勤務地・給与)。職種は1求人につき1〜3つ選択する(兼務ポジションに対応しつつ、検索に多く出るための付けすぎを防ぐため上限を3つとする)
  6. 選考フロー(「カジュアル面談 → 一次面接 → 最終面接」のようなステップ表示。1〜6ステップ)
  - 雇用形態: 正社員 / 契約社員 / アルバイト / 業務委託 / インターン
  - 給与は月給で統一する(年収表記は賞与・残業代込みで高く見せられるため)
  - 月給は範囲(下限〜上限)ではなく1つの金額で掲載する(例: 月給40万円)。範囲だと上限に期待して応募しがちで、求職者が実際の金額を判断しにくいため。受け付ける金額は10万〜200万円
  - 同時に公開できる求人は1社10件まで(下書き・募集終了は数えない)。同じような求人の大量掲載で検索結果を独占されるのを防ぎ、企業側にも求人を厳選させるため
  - 求人一覧の各求人にはいいね数(=応募数)を表示する
- 応募者(いいねしてきた求職者)一覧・プロフィール閲覧(生年月日は年齢に変換して表示)
  - 求人ごとの絞り込み
- 求人の状態: 下書き → 公開中 → 募集終了。募集終了後も「募集再開」で公開中に戻せる
  - 募集終了しても、反応待ちの応募はそのまま残る(企業は引き続きマッチ・見送りを返せる)。求人一覧・詳細に反応待ちの件数を警告表示する
  - いいねが1件でもある求人は削除できない(募集終了のみ)。削除できるのはいいね0件の求人だけ
- 応募者一覧は「反応待ち」「マッチ」「不成立」のタブで切り替え、求人ごとに絞り込める
- 応募者への「気になる」でマッチ成立、「見送り」で不成立(7日以内にどちらも返さないと自動不成立)
  - マッチ成立後、応募者詳細に求職者のメールアドレスを表示する。以降の連絡は企業がメールで行う
- 通知(新しい応募。アプリ内通知のみ)

## 5. 非機能要件

- レスポンシブ対応(PCブラウザ想定、スマホも考慮)
- デザイン: 角丸を使わない角張ったデザイン(太い枠線+ずらした影)。配色は薄い水色と白がメイン、差し色に紺と赤。ダークモードは対応しない。採用したデザイン案: [design/job-search-b-revised.png](design/job-search-b-revised.png)
- ローカル開発からDockerを使用
- Railwayへデプロイ
- セキュリティ: CSRF対策(Sanctum標準)、XSS対策、入力バリデーション

## 7. 主要データモデル(ドラフト)

- `users`(求職者)
- `work_experiences` / `educations` / `certifications`(求職者の職歴・学歴・資格)
- `companies`(企業。1社1アカウントとしてログイン主体を兼ねる。企業ページの各項目を含む)
- `job_postings`(求人。公開/非公開ステータスを含む)
- `job_posting_images`(求人の画像ギャラリー)
- `companies`の写真ギャラリー(`company_images`)
- 技術スタックタグのマスタ(企業・求人で共通。選択式)と、企業・求人それぞれとの中間テーブル
- 職種のマスタと、求人との中間テーブル(1求人につき1〜3件)
- 選考フローのステップ(持ち方はDB設計時に決定)
- `likes`(いいね=応募。マッチ成立可否・志望動機・スーパーいいね区別を含む)
- `bookmarks`(求職者の求人ブックマーク)
- `notifications`
